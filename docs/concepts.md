# Wishes 核心概念

> [!NOTE]
>
> 本文档面向希望**理解 `Wishes` 内部模型**或**自定义卡池**的用户。
>
> 你不需要具备编程背景 —— 本文会用自然语言描述 `Wishes` 的运作方式。
>
> 本文档由 AI 工具整理生成，并经过人工审核。

`Wishes` 的灵活性来源于一组小巧而通用的抽象。
理解本文档中的概念后，你将能够**从零构建任意卡池** —— 无论是模拟某款游戏的完整抽卡机制，还是搭建自定义的随机系统。

## 一、设计哲学

`Wishes` 的设计围绕三个核心思想展开：

**第一, 一切皆标签。**
在大多数抽卡工具中，"稀有度"、"类型"、"所属游戏" 这些属性往往被写死在程序里。而 `Wishes` 选择把 **所有描述性信息** 统一抽象成"标签" —— 无论是卡片属性、卡池归属，还是抽卡结果的分组，都用同一种方式表达。这使得系统可以适配任何游戏，而不需要为每款游戏单独编写代码。

**第二, 逻辑与数据分离。**
`Wishes` 把"抽卡"拆成两个互相独立的问题：

- **抽卡逻辑** 只负责回答："这一抽应该命中什么类型的卡片？"
- **卡组** 只负责回答："符合这个类型的卡片有哪些？"

两者之间通过**标签**这一中间层沟通，彼此不知道对方的具体实现。带来的好处是：

- **逻辑可复用** —— 同一份抽卡逻辑可以驱动多个卡池。
- **数据可扩展** —— 新增游戏、新增卡池通常只需要添加数据文件，无需改动程序。

**第三, 数据只读而可分叉。**
官方数据与拓展包数据在运行时**永远只读**。用户对它们的任何编辑都不会原地修改，而是**派生**出一个本地副本。
由此，官方数据的完整性、拓展包的可叠加性、用户数据的可自定义性可以同时成立 —— 三方数据不会互相冲突。

## 二、标签：描述事物的统一方式

### 2.1 普通标签

一个**标签**由两部分组成：

- **命名空间** —— 描述"这是关于什么的"，例如 `rarity`(稀有度)、`type`(类型)、`game`(游戏名)。
- **值** —— 描述"具体是什么"，例如 `5`、`character`、`genshin`。

写在一起时用冒号分隔，例如 `rarity:5`、`type:character`、`game:genshin`。

两个标签相等，只有当**命名空间和值都相同**才算。这意味着 `type:character` 与 `rarity:character` 是两个不同的标签 —— 尽管它们的值都是 `character`，但描述的是不同方面的属性。

`Wishes` 内置了三个常用命名空间：

| 命名空间 | 用途 | 示例 |
| :--- | :--- | :--- |
| `game` | 游戏名 | `game:genshin` |
| `type` | 对象类型 | `type:character`、`type:weapon` |
| `rarity` | 稀有度 | `rarity:5`、`rarity:4` |

当然，你也可以自由使用其他命名空间，例如 `element:pyro`(火元素)、`path:destruction`(毁灭命途) 等。

### 2.2 活动标签

**活动标签**是标签系统的一个特殊类别：它**只有值，没有命名空间**。

它的用途不是描述卡片的固有属性，而是描述 **"这一次抽卡的结果应该归属哪个活动分组"**。常见的有 `up`(概率提升)、`standard`(常规)、`fes`(节日限定)、`appoint`(定轨)。

为什么需要活动标签？考虑一个典型场景：

> 同一张五星角色卡，在**卡池 A** 中可能只是一张普通卡片 (`standard`)，但在**卡池 B** 中可能成为概率提升卡片 (`up`)。

如果直接把"是否 UP"写死在卡片上，就丧失了这种动态性 —— 一张卡片无法同时属于两个不同的活动分组。

活动标签的设计正是为了解决这一点：它**不附着在卡片上**，而是由**抽卡逻辑在每次抽卡时动态产生**。同一张卡片，在不同的卡池中自然拥有不同的活动归属。

### 2.3 标签化

`Wishes` 中所有核心对象 —— 卡片、卡组、卡池、逻辑 —— 都可以**附带一组标签**。当你描述一个对象时，标签就是你给它贴上的"关键词"。

例如，一张卡片可能同时带有 `rarity:5`、`type:character`、`game:genshin` 三个标签。系统正是通过这些标签来理解"这张卡片是什么"。

## 三、来源与分叉

### 3.1 三种来源

`Wishes` 中的所有核心对象（卡片 / 卡组 / 逻辑 / 卡池）都带有一个 **来源** 字段，标明它来自哪里：

| 来源 | 含义 | 存储位置 | 可写 |
| :--- | :--- | :--- | :---: |
| `official` | 官方数据 | `data/official/` | ✗ |
| `local` | 用户数据 | `data/local/` | ✓ |
| `pack:<name>` | 拓展包数据 | `data/packs/<name>/` | ✗ |

官方数据与拓展包数据在运行时**永远只读**，用户的所有创作都写入 `local`。

### 3.2 分叉：编辑只读对象的方式

当你想修改一个 **只读来源** 的对象时（比如想把官方卡片的名字改掉），`Wishes` 不会原地修改它。取而代之，系统会：

1. 复制该对象的全部内容。
2. 分配一个新的 `GlobalId`。
3. 把来源改为 `local`，并记录 `forked_from` 指向原对象。
4. 把派生副本写入 `data/local/`。

原对象保持不变，也**永远不会被修改**。这一过程称为 **分叉**（fork）。

分叉带来的好处是：

- **官方数据永不被污染** —— 即使你误操作，官方数据也能保持完整。
- **冲突不可能发生** —— 用户数据与官方数据在物理上分离，官方更新时不会覆盖你的修改。
- **可追溯** —— 派生对象通过 `forked_from` 记录它的来源，从哪张官方卡片改来的，一目了然。

### 3.3 遮蔽：当前生效的是哪个版本

分叉产生之后，原对象和派生对象同时存在于系统中，但它们**不应同时生效** —— 否则抽卡时可能随机抽到任一版本，用户会困惑："我明明编辑了，为什么还会抽到旧版？"

**遮蔽**（shadow）就是用来解决这个问题的开关：

- **派生对象遮蔽原对象（默认）**：
  - 原对象在卡片列表、卡池抽卡中**不可见**。
  - 卡组中引用原对象的 `include_ids` / `exclude_ids` 在**解析时**被覆盖层重定向到派生对象，卡组文件本身不会被改写。
  - 抽卡时只能抽到派生对象。
- **派生对象不遮蔽原对象**：
  - 两个版本在列表中**同时可见**。
  - 卡组的引用保留指向原对象。
  - 抽卡时抽到的是原对象；派生对象更像是一个"草稿"。

用户可以随时切换遮蔽状态：

- **撤销遮蔽**：原对象重新可见，引用解析回原对象。抽卡立刻生效于原版本。
- **重新启用遮蔽**：原对象再次隐藏，引用解析到派生对象。

> [!NOTE]
>
> **引用覆盖层**：遮蔽产生的引用重定向不会写回任何 JSON 文件，而是保存在本地数据库 `db/overrides.db` 中，按对象类型分表（Card / Deck / Logic，当前启用 Card）。卡池对卡组的引用覆盖将随 Banner CRUD 一起启用。

遮蔽的语义可以概括为一句话：**"当前生效的是哪个版本"**。
它并不改变数据的存储方式，只决定哪个版本参与列表展示与抽卡。

> [!NOTE]
>
> 当前 UI 中，**卡片**可以在编辑时选择是否遮蔽，也支持在详情页随时切换；**卡组**的分叉默认遮蔽，手动切换的功能将在后续版本加入。

### 3.4 删除派生对象

删除派生对象后：

- 原对象**自动恢复可见**。
- 引用覆盖随之解除：卡组中原本指向原对象的引用恢复生效，卡组文件从未被改写。

也就是说，删除派生对象等于"放弃自己的修改，回到官方版本"。
若某个卡组显式引用了派生对象自身的 Id（例如在派生之后新建的卡组），删除后该引用会像删除任何本地卡片一样失效。

### 3.5 一个原对象最多一个派生

为了避免引用关系的混乱，`Wishes` 规定：**一个原对象最多只能有一个派生对象**。

如果你已经分叉了一张官方卡片，再次尝试编辑它会被拒绝，并提示你直接编辑已有的派生版本；如果想重新从官方版本开始，需要**先删除派生对象**，再重新分叉。

## 四、卡片

**卡片**是抽卡流程中最基本的产出对象。

每张卡片有以下几个核心字段：

- **GlobalId** —— 全局唯一的标识（Uuid v7），创建时生成，永不变更。
- **来源** —— 上文所述的 `official` / `local` / `pack:<name>`。
- **内容** —— 卡片展示的文本，例如角色名、道具名。内容是 **多语言映射**（语言标签 → 文本），例如同时携带 `zh-CN: "胡桃"` 和 `en: "Hu Tao"`。
- **称号 / 副标题** —— 可选字段，同样是多语言映射。
- **标签** —— 用于描述它的属性。

内容允许重复 —— 两张卡片可以叫同一个名字，只要 `GlobalId` 不同。

> [!NOTE]
>
> 卡片的**立绘**（美术资源）字段计划在未来版本中补充。

## 五、卡组

**卡组**是"候选卡片池"的定义。它的核心特点是：

> 卡组**不存储卡片列表**，而是通过**一套筛选规则**动态计算成员。

这意味着当卡片发生变化时（如新增一张五星角色），卡组会自动把符合条件的卡片纳入进来，无需手动维护。

### 5.1 成员规则

成员规则由一组**有序的**条件组成，按声明顺序依次应用。条件分为以下几类：

**包含型条件** —— 从全局搜索符合条件的卡片，并入当前结果：

- **拥有全部标签** —— 找出同时具备指定所有标签的卡片。
- **拥有任意标签** —— 找出具备任一指定标签的卡片。
- **指定 GlobalId** —— 直接添加指定标识的卡片。

**过滤型条件** —— 在当前结果中进一步筛选：

- **保留全部标签** —— 在当前结果中，只保留同时具备指定所有标签的卡片。
- **保留任意标签** —— 在当前结果中，只保留具备任一指定标签的卡片。

**排除型条件** —— 从结果中移除：

- **排除指定 GlobalId** —— 直接移除指定标识的卡片。

#### 执行顺序

条件的**声明顺序很重要**。系统分两个阶段处理：

1. **第一阶段**：按声明顺序应用所有**包含型**和**过滤型**条件。
   这里顺序敏感 —— "拥有全部标签"是与当前结果合并，而"保留全部标签"是与当前结果取交集，调换位置会导致不同的结果。
2. **第二阶段**：统一应用所有**排除型**条件。
   无论"排除指定 GlobalId"写在哪个位置，都在最后生效。

最终，卡组的成员就是经过上述所有条件筛选后剩下的卡片集合。

### 5.2 活动组

**活动组**是在成员基础上的**进一步筛选**，用于描述"某个活动标签下实际包含哪些卡片"。

例如，一个卡池可能包含"所有五星角色"，其中一部分被标记为 `up`(概率提升)，另一部分作为 `standard`(常规)。活动组就是用来定义"哪些成员属于 `up`、哪些属于 `standard`"的规则。

活动组的条件类型与成员规则基本一致，此外还额外支持：

- **全选** —— 取全部成员。
- **引用其他活动组** —— 复用其他活动组的规则 (*暂未实现*)。

#### 一个重要的约束

> 活动组的结果**必须是卡组成员的子集**。

即使活动组的条件使用了"拥有全部标签"这类全局搜索，最终结果也会与卡组成员取交集。这保证了活动组里不会出现"不属于这个卡组"的卡片。

### 5.3 卡片查询

当系统要"根据标签找出候选卡片"时，会依次进行以下步骤：

1. 计算卡组的所有成员。
2. 如果抽卡逻辑给出了普通标签条件，与全库中符合这些标签的卡片取交集。
3. 对每个活动标签，查询对应的活动组并进一步过滤；**如果某个活动标签没有对应的活动组，直接返回空结果**。
4. 返回所有满足条件的卡片编号。

这一流程由程序自动完成，你只需要在配置卡组时声明好规则即可。

## 六、抽卡逻辑

**抽卡逻辑**负责产出"这一抽应该命中什么类型的卡片"。它的输出用**标签**表达，而不是具体的卡片。

逻辑分为两部分：**静态定义**与**运行时状态**。

### 6.1 逻辑定义

**逻辑定义**是静态的蓝图，描述"这个逻辑是什么"、"采用哪种实现方式"。

`Wishes` 支持两种逻辑实现方式：

- **硬编码逻辑** —— 由程序内部直接实现，性能好，适合模拟具体游戏的复杂机制 (如原神的捕获明光)。
- **规则链逻辑** —— 由一系列可组合的规则组成 (*规则执行器尚在开发中*)。

目前 `Wishes` 内置了以下硬编码逻辑：

| 名称 | 说明 |
| :--- | :--- |
| 原神角色 UP | 含捕获明光机制 |
| 崩坏:星穹铁道角色 UP | 标准大小保底 |

### 6.2 运行时状态

**运行时状态**是逻辑定义在**某个具体卡池中的进度**。

例如，原神角色 UP 的逻辑状态会记录：

- 距离上次五星已抽多少抽
- 距离上次四星已抽多少抽
- 下一个五星是否为大保底
- 捕获明光计数器

但请注意：**逻辑状态（由逻辑自由定义的 JSON）** 与 **卡池运行时状态** 是两个层次的概念。卡池运行时状态是一个结构化的对象，包含：

- **总抽数** —— 该作用域下累计抽了多少次。
- **逻辑状态** —— 由逻辑定义自由定义、由逻辑执行时更新的 JSON。

卡池运行时状态以 **状态作用域** 为键（见下一节）。逻辑定义可以被多个卡池共享，但每个作用域的状态是**独立的**。

### 6.3 逻辑结果

逻辑执行结束后，会产生一个**逻辑结果**，包含两组信息：

- **普通标签条件** —— 描述"抽中了什么类型的卡片"，例如"五星角色"。
- **活动标签条件** —— 描述"这次抽卡属于哪个活动分组"，例如 `up` 或 `standard`。

逻辑结果就是**逻辑与卡组之间的"接口"**：逻辑只关心输出什么标签组合，卡组只关心这些标签能匹配到什么卡片。

## 七、卡池

**卡池**是面向用户的抽卡入口，它把**卡组**和**逻辑**绑定在一起。

一个卡池 = **一份卡组** + **一份逻辑定义** + **一份状态作用域**。

- 多个卡池可以引用**同一个卡组** —— 例如"原神角色 UP 池"和"原神角色常驻池"可能共享候选卡片池。
- 多个卡池也可以引用**同一个逻辑定义** —— 例如多个 UP 池都用"原神角色 UP"逻辑。
- 每个卡池的 **状态作用域** 决定了它的运行时进度是否与其他卡池共享。

### 7.1 状态作用域

状态作用域是一个字符串键，有两种形式：

- `banner`（默认）：每个卡池**独立**维护自己的状态。修改一个卡池的保底计数，不会影响其他卡池。
- `group:<name>`：同组的多个卡池**共享**同一份状态。例如明日方舟标准池的保底进度会在不同 UP 池之间继承，就可以把它们归入同一个 group。

这是 `Wishes` 支持"跨池继承保底"等机制的基础。

## 八、一次抽卡发生了什么

当你在界面上点击"抽卡"按钮时，`Wishes` 内部依次做了这些事：

**第一步, 锁定卡池。**
系统获取目标卡池，并暂时锁定它，避免同一时刻有两个抽卡请求修改同一个状态。

**第二步, 读取计数器。**
从卡池对应的 **状态作用域** 中读取"这个作用域已经抽了多少次"。

**第三步, 生成随机种子。**
系统将"用户 + 卡池 + 抽数"混合成一个**确定性的随机种子**。
由于种子是确定的，同样的输入必然得到同样的结果 —— 这意味着**每一次抽卡都是可复现的**。

**第四步, 执行抽卡逻辑。**
逻辑定义执行对应的实现，产出一个逻辑结果 (包含普通标签条件和活动标签条件)，并更新逻辑状态。

**第五步, 查询候选卡片。**
把逻辑结果交给卡组，卡组根据标签条件筛选出所有符合条件的卡片。

**第六步, 随机选取一张。**
在所有候选卡片中**等概率**随机选取一张。

**第七步, 更新状态。**
把"已抽数 +1"以及新的逻辑状态写回 **状态作用域**，并持久化保存到 `SQLite`。

**第八步, 返回结果。**
把抽到的卡片 (附带本次抽卡的活动标签) 返回给界面展示。

### 关于确定性随机

目前 `Wishes` 的抽卡是**可复现的**：只要用户、卡池、抽数这三个条件相同，结果就必然相同。这一设计带来两个好处：

- **可审计** —— 任何一次抽卡结果都可以被重新验证。
- **可测试** —— 开发者可以精确验证边界行为 (如"第 90 抽必出五星")。

> [!NOTE]
>
> 当前 `Wishes` 的随机种子为简化实现，采用 `本地用户 Id + 卡池 Id + 累计抽数` 的方式构建。
>
> 未来会更换随机种子的构建方式，使得不同设备结果不同，但保留可复现性。

## 九、概念之间的关系

用一句话概括这些概念的协作方式：

> **卡池**引用一份**卡组**和一份**逻辑定义**，并关联一个**状态作用域**。**逻辑**执行后产出**逻辑结果**。**逻辑结果**交给**卡组**，由卡组根据标签条件筛选出**卡片**。最终被选中的卡片就是本次抽卡的结果。

更具体地说：

- **卡片** 是静态数据，带有标签、多语言内容与来源。
- **卡组** 是基于标签的规则集合，动态计算成员。
- **逻辑定义** 是抽卡机制的静态蓝图。
- **状态作用域** 是卡池进度的持久化单位，可以独立，也可以多个卡池共享。
- **逻辑结果** 是逻辑与卡组之间沟通的中间产物。
- **卡池** 是上述所有元素的组合，也是用户直接交互的对象。
- **分叉** 是用户编辑只读来源对象时采用的方式，它保持官方数据不受污染。

## 十、创建一个自定义卡池

假设你想要模拟一个自定义游戏的卡池，大致步骤如下。

### 第一步: 准备卡片

在数据目录的卡片文件夹中添加卡片，为每张卡片指定内容和标签。

如果你使用图形界面，可以直接在 *图鉴 → 卡片* 面板中创建。

### 第二步: 创建卡组

新建一个卡组，声明：

- **成员规则** —— 定义哪些卡片属于这个卡组。
- **活动组规则** —— 定义每个活动分组中包含哪些卡片。
- **标签** (可选) —— 给卡组本身附加的标签。

### 第三步: 选择或定义抽卡逻辑

你可以直接使用 `Wishes` 内置的硬编码逻辑，也可以等待未来的自定义规则链功能。

> [!NOTE]
> 内置逻辑目前支持原神与崩坏:星穹铁道两种角色 UP 池。

### 第四步: 创建卡池

创建一个卡池，将上面的卡组和逻辑绑定在一起，并为逻辑设置初始状态 (例如初始保底计数为 0)，并指定状态作用域 (`banner` 或 `group:<name>`)。

### 第五步: 启动与验证

启动 `Wishes` 后，加载程序会自动进行以下校验：

1. **数据格式版本** —— 读取数据目录根部的 `version.json`，版本不符时直接失败（**不做自动迁移**）。
2. **GlobalId 唯一性** —— 所有对象的 `GlobalId` 跨来源不可重复。
3. **来源一致性** —— 数据文件中声明的来源必须与其物理所在目录一致。
4. **引用完整性** —— 卡池引用的卡组和逻辑定义必须存在。
5. **覆盖性校验** —— 卡组必须能匹配逻辑的**所有可能输出组合**。如果某个输出组合找不到候选卡片，加载会失败并提示缺失的组合。

如果校验通过，卡池就会出现在主页，可以开始抽卡。

> [!NOTE]
> 卡池和抽卡逻辑的编辑 UI 需等待后续版本完善。
